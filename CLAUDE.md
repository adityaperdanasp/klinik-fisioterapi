# Klinik Fisioterapi — App Internal (Bekasi)

App name: **Pulih Fisioterapi**. Status: **Fase 1 selesai** (semua 5 fitur di bawah sudah dibangun dan live di production). Ini file panduan buat kerja lanjutan (bugfix, penyesuaian, Fase 2).

## Konteks Bisnis

Klinik fisioterapi spesialisasi cedera otot di Bekasi. Partner: Adit (fisioterapis, STR ada), Erwin, Maikel.

- Kapasitas: 4 fisioterapis × 4 ruang, sesi 50 menit, 7 jam efektif/hari, 26 hari/bulan → maksimum 874 sesi/bulan.
- BEP: 290 sesi/bulan (~33% dari kapasitas maksimum).
- Tarif default: Rp175.000/sesi — disimpan di tabel `settings` (key `tarif_default`), bukan hardcode.
- Ramp-up asumsi: utilisasi 15% → 65% linear bulan 1–12. Bulan ke-1 dihitung dari `settings.bulan_mulai_operasional` (lihat TODO di bawah — masih placeholder).
- Model finansial lengkap ada di Google Sheet (link tidak disertakan di sini — tanya Adit kalau perlu referensi angka).

**Catatan penting:** status perizinan klinik dan harga alat medis masih belum final. Jangan asumsikan fitur billing asuransi/BPJS dibutuhkan kecuali diminta eksplisit — belum ada keputusan soal itu.

## Migrasi Supabase → Firebase — status: SEDANG BERJALAN (Fase 1 selesai)

Keputusan user: pindah backend dari Supabase ke Firebase. Alasan awal ("Firebase gratis, Supabase bakal bayar") sebenarnya keliru — dua-duanya gratis di skala pemakaian sekarang, bedanya cuma Supabase free tier auto-pause kalau idle 7 hari (sudah di-fix terpisah, lihat gotcha). User tetap milih lanjut migrasi setelah dikasih tau tradeoff-nya — jangan re-litigate keputusan ini, cuma eksekusi sesuai fase.

**Karena belum ada data pasien/booking/payment ASLI (masih dummy)**, migrasi ini rebuild skema baru langsung di Firestore, BUKAN proses export/import data sensitif.

Rencana 7 fase (kerjain satu-satu, verifikasi tiap fase sebelum lanjut):
1. ✅ **Setup project Firebase** — project `pulih-fisioterapi`, Firestore (region `asia-southeast2`/Jakarta, delete protection ON), Auth provider Email/Password + Google keduanya enabled, web app terdaftar, service account Admin SDK udah di `.env.local` (`lib/firebase/client.ts` + `lib/firebase/admin.ts`). Smoke-test read/write Firestore + Auth API berhasil.
2. ✅ **Auth**: Supabase Auth → Firebase Auth. `/login` (server action, sign-in via REST API `identitytoolkit.googleapis.com`) → `adminAuth.createSessionCookie()` → httpOnly cookie `session`. `proxy.ts` (Edge runtime) verifikasi cookie pakai `lib/firebase/edge-verify.ts` (JWT verify manual pakai `jose`, BUKAN Admin SDK — Admin SDK butuh Node crypto, nggak jalan di Edge). `lib/current-user.ts` & logout tetap pakai Admin SDK biasa (jalan di Node runtime/Server Component). Role disimpan di Firestore `profiles/{uid}` (bukan custom claims). Diverifikasi end-to-end: login → role muncul benar di nav → logout → proteksi route redirect ke `/login` kalau belum login.
3. ✅ **Skema Firestore**: didokumentasikan lengkap di `lib/firebase/schema.ts` (tipe TypeScript + nama koleksi, jangan reimplement magic string koleksi di file lain — import dari situ). Keputusan desain penting (beda dari Postgres): `patient_medical_info/{patientId}`, `session_notes/{bookingId}`, `payments/{bookingId}` pakai id dokumen yang SAMA dengan id induknya (pengganti relasi 1:1 + UNIQUE constraint Postgres — sekalian gratis anti-duplikat). `settings/{key}` pakai key aslinya sebagai doc id. Nomor rekam medis (dulu Postgres sequence) diganti counter manual `counters/patients` (field `next`), WAJIB di-increment lewat Firestore transaction pas dipakai nanti (Fase 5), jangan read-then-write biasa. Data referensi (`rooms` 4 ruang, `physiotherapists` 4 fisio placeholder, `settings` 4 key bisnis) udah di-seed via `scripts/seed-firestore.mjs` (idempotent, aman dijalanin ulang — `node scripts/seed-firestore.mjs`), isinya sama persis kayak seed Supabase lama biar konsisten.
4. ✅ **Anti-bentrok jadwal**: `lib/firebase/bookings.ts` (`createBooking`, `rescheduleBooking`). Firestore nggak punya EXCLUDE constraint kayak Postgres, jadi dicek manual di dalam `runTransaction` — query `physiotherapist_id == X AND starts_at < ends_at_baru` (cuma 1 field range, sisanya `ends_at > starts_at_baru` & `status != 'cancelled'` disaring manual di kode), sama buat `room_id`. Query di dalam transaction otomatis included di read-set-nya, jadi race condition (2 booking bentrok dibuat bersamaan) otomatis kena retry oleh Firestore — setara constraint level-database. **Butuh composite index** (`physiotherapist_id + starts_at`, `room_id + starts_at`) — udah dideploy via `firestore.indexes.json` + `firebase deploy --only firestore:indexes`. Diverifikasi pakai test suite manual (5/5 pass): booking normal, bentrok fisio, bentrok ruang, nggak overlap, dan slot ke-cancel bisa dipakai ulang. `firestore.rules` sengaja masih default-deny total (placeholder) — itu Fase 6, belum ada akses client SDK sama sekali sekarang (semua lewat Admin SDK di server).

## Gotcha teknis (biar nggak keulang)

- **Timezone (date-key kalender)**: jangan pernah pakai `.toISOString().slice(0,10)` buat bikin date-key kalender — WIB itu UTC+7, konversi ke UTC bisa geser tanggal mundur. Pakai `toDateKey()` di [lib/week.ts](lib/week.ts) (berbasis `getFullYear/getMonth/getDate` lokal), jangan reimplement.
- **Timezone (format tampilan jam/tanggal)**: `toLocaleDateString`/`toLocaleTimeString`/`toLocaleString` TANPA opsi `timeZone: "Asia/Jakarta"` eksplisit bakal ngikut timezone runtime SERVER, bukan WIB — di dev lokal biasanya nggak kelihatan bug-nya (mesin dev kebetulan udah WIB), tapi di Vercel production (default UTC) jam/tanggal bisa geser sampai 7 jam / 1 hari. Ini CUMA masalah kalau Date-nya dibikin dari timestamp asli (ISO string dari Firestore/API, misal `starts_at`, `paid_at`) — Date yang dibikin dari komponen lokal (`new Date(y, m, d, ...)` atau `new Date(\`${dateKey}T00:00:00\`)`, pola yang sama kayak `toDateKey`) aman, nggak perlu opsi ini karena parse & format-nya konsisten sendiri. `formatTime()` di `lib/week.ts` udah di-pin, tapi kalau nulis `new Date(iso).toLocaleXxx(...)` baru di tempat lain, WAJIB tambahin `timeZone: "Asia/Jakarta"`.
- **Supabase embedded relation cardinality**: tanpa generated types, `select("...,table(col)")` bisa balikin objek tunggal ATAU array tergantung ada tidaknya `UNIQUE` constraint di foreign key-nya — cek dulu sebelum asumsi salah satu (contoh: `payments.booking_id` UNIQUE → objek tunggal, bukan array).
- **Next.js 16**: `middleware.ts` sudah deprecated, pakai `proxy.ts` dengan named export `proxy` (bukan `middleware`).
- File `.env.local` isinya publishable/anon key doang (aman) — jangan pernah taruh `service_role` key di sana atau di kode manapun yang bisa ke-bundle ke client.
- **`proxy.ts` matcher** harus exclude semua ekstensi asset publik yang dipakai, bukan cuma gambar. Pernah kejadian: matcher cuma exclude `svg|png|jpg|jpeg|gif|webp`, jadi request ke `/videos/*.mp4` ke-anggap "halaman" dan di-redirect ke `/login`. Kalau nambah jenis asset baru di `public/` (video, audio, dll), cek dulu matcher regex-nya ikut di-update.
- Foto/video besar (dari kamera/stok, bisa puluhan MB) **wajib dikompres dulu** sebelum masuk `public/` — pakai `sips` (image) atau `ffmpeg` (video, scale + `-crf 28` + strip audio kalau nggak perlu) sampai ukuran wajar (puluhan-ratusan KB), baru commit. Jangan commit file asli yang belum dikompres.
- **`firebase-admin` NGGAK bisa dipake di `proxy.ts`/middleware** — proxy.ts jalan di Next.js Edge runtime, Admin SDK butuh Node crypto/gRPC yang nggak tersedia di sana. Verifikasi session cookie di Edge pakai `lib/firebase/edge-verify.ts` (manual JWT verify pakai `jose` + public key dari `identitytoolkit/v3/relyingparty/publicKeys`), BUKAN `adminAuth.verifySessionCookie()`. Admin SDK tetap boleh dipake bebas di Server Component/Route Handler/Server Action (jalan di Node runtime).
- **Firestore composite index**: query yang gabungin equality (`==`) + range (`<`/`>`) di 2 field BEDA (mis. `physiotherapist_id == X AND starts_at < Y`) itu TIDAK ke-cover automatic index bawaan Firestore — wajib bikin composite index manual, kalau nggak bakal error `FAILED_PRECONDITION` pas runtime. Kelola lewat `firestore.indexes.json` (deploy: `firebase deploy --only firestore:indexes --project pulih-fisioterapi`), jangan cuma klik link error-nya doang (nggak ke-track di repo). Index baru butuh waktu buat "build" (`state: CREATING` → `READY`, biasa beberapa menit) sebelum bisa dipakai — kalau nambah query compound baru, jangan langsung tes, cek state-nya dulu.
- **Firestore `Timestamp` nggak bisa dioper ke Client Component** — Server Component boleh manggil `adminDb`/baca `Timestamp` bebas, tapi begitu mau nge-pass data itu sebagai props ke komponen `"use client"`, WAJIB di-strip/convert dulu (pilih field manual atau `.toDate().toISOString()`), jangan spread seluruh dokumen (`{ id, ...data }`) langsung ke props client component — bakal error "Only plain objects... can be passed to Client Components" tapi errornya BARU muncul di browser console/log runtime, bukan di `tsc --noEmit` (TypeScript nggak nangkep ini kalau tipenya di-cast manual). Cek tiap kali bikin props baru ke client component dari data Firestore.
- Akun test buat login internal: `admin-test@pulihfisioterapi.id` / role `admin` (password dikasih ke user lewat chat, sengaja nggak ditulis plaintext di sini) — cuma buat testing selama migrasi, ganti/hapus sebelum go-live.
- **`firebase-admin` butuh `jose` versi CJS-compatible** — `firebase-admin/auth` (lewat dependency `jwks-rsa`) manggil `require("jose")`. `jose` v5+ itu ESM-only (nggak ada build CJS sama sekali), jadi bakal SELALU error `ERR_REQUIRE_ESM` di production Vercel (nggak kejadian di `npm run dev` lokal, cuma muncul di serverless function beneran — jangan tertipu kalau dev lokal "kelihatan" fine). Fix: `package.json` di-pin `"jose": "4.15.9"` + `"overrides": { "jose": "4.15.9" }` (v4 itu dual-package, punya build CJS & ESM). **Jangan pernah `npm update jose` atau hapus override ini** tanpa tes production dulu. `next.config.ts` juga ada `serverExternalPackages: ["firebase-admin"]` (perlu tapi nggak cukup sendirian — akar masalahnya di versi `jose`, bukan bundling).
